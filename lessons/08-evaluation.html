Harness Engineering · Module 08

Evaluating harnesses honestly

Almost every published agent number is a joint measurement of a model and a harness, reported as if it were a property of the model. Once you see that confound you cannot unsee it — and it changes how you read the field and how you report your own results.

Reading + walkthrough + quizlab/w08_ablation.py45 minCompiled by Premansh Panigrahi

Section 1The confound

The cleanest available demonstration, from Terminal Bench 2.0:

ConfigurationApproximate rank
Claude Opus 4.6 inside Claude Code~#33
Claude Opus 4.6 inside a custom harness~#5

Same weights. Same benchmark. The variable was the harness — its tools, its prompt, its feedback signals, its loop. This figure circulates through Trivedy and HumanLayer and I have not verified it against the leaderboard directly, so treat the exact ranks as approximate. The magnitude of the effect is the point, and it is corroborated by Trivedy's team independently moving an agent from Top 30 to Top 5 by changing only the harness.

There is a mechanism for this, and it is not "custom harnesses are just better":

Models get post-training coupled to the harness they were trained against. Moving them into a different harness — with better tools for your codebase, a tighter prompt, and sharper back-pressure — can unlock capability the original harness was leaving on the floor.Addy Osmani, paraphrasing the mechanism

Section 2The HarnessCard

He et al. (Preprints.org 202603.1756) argue that harness configuration should be reported alongside results as a matter of course, and propose a standard disclosure. Their required fields:

FieldWhat it captures
Model + versionExact checkpoint, not "Claude"
Tool inventory & permissionsWhat the agent could do, and what was gated
Context policyCompaction, offloading, retrieval, window management
State / memory designWhat persists, in what format, across what boundary
Loop & stop conditionsIteration structure and every termination criterion
Feedback stackTests, graders, human checkpoints — what signals reached the agent
GovernanceSandboxing, approvals, provenance logging
Eval protocolTask set, number of runs, variance, outcome criteria, budget limits

I would treat this as a well-argued proposal rather than an adopted standard — it is a preprint, and adoption is currently near zero. But the fields are a good self-audit even if nobody else ever reads your card. If you cannot fill one in for your own system, you do not know your own system.

Section 3Capability framings

NVIDIA's developer blog offers a complementary lens: rather than listing components, enumerate the capabilities a harness provides and evaluate whether each is present and working. Their framing centres on things like environment setup and tool access, context management, planning and decomposition, verification and self-correction, error recovery, and observability.

The value is as a checklist against blind spots. Component lists tend to reflect what your framework happens to ship. Capability lists ask what the agent actually needs, which surfaces the gaps — most commonly error recovery and observability, which no framework makes you configure and which nothing forces you to notice are missing.

configuration       ctx chars     rm -rf   shipped broken
------------------------------------------------------------
full harness            1,490    blocked               no
− permissions           1,490        RAN               no  ( 1.0x)
− back-pressure         1,442    blocked              YES  ( 1.0x)
− truncation            8,263    blocked               no  ( 5.5x)
− context policy        5,280    blocked               no  ( 3.5x)
bare loop              32,280        RAN              YES  (21.7x)

Each removed component maps to exactly one degraded column. That one-to-one mapping is the definition of load-bearing. Remove permissions, the destructive command runs. Remove back-pressure, the agent ships broken work. Remove either context control, the window inflates 3.5–5.5x. Remove everything, all three fail and context is 21.7x the baseline.

A component that changes no column under ablation is not load-bearing. It is cost.

Section 5Check your understanding

Quiz · Module 08

The Terminal Bench 2.0 figure (~#33 vs ~#5) is used here to show…
Why: Same weights, different harness, wildly different rank. The effect is a harness effect. I flag the exact ranks as approximate (not verified on the leaderboard); the magnitude is the point.
In the ablation table, a component that changes NO column is…
Why: Load-bearing means exactly one degraded column appears when you remove it. No change means it does nothing observable — you are paying for it for nothing.
The HarnessCard (He et al.) is treated here as…
Why: It is a preprint with near-zero adoption. The fields are a good self-audit — if you can't fill one in, you don't know your own system — but I don't present it as settled.
Why does this module insist on running an ablation n > 1 against a real model?
Why: The deterministic fake model is perfect for teaching method, but a real model's run-to-run variance means a single run can't distinguish signal from noise. Report variance, or you haven't measured.
