Harness Engineering · Module 08

Evaluating harnesses honestly

Almost every published agent benchmark number is a joint measurement of a model and a harness, reported as if it were a property of the model. Once you see that confound you cannot unsee it — and it changes how you read the field and how you report your own results.

Section 1The confound

The cleanest available demonstration, from Terminal Bench 2.0:

ConfigurationApproximate rank
Claude Opus 4.6 inside Claude Code~#33
Claude Opus 4.6 inside a custom harness~#5

Same weights. Same benchmark. The variable was the harness — its tools, its prompt, its feedback signals, its loop. This figure circulates through Trivedy's and HumanLayer's write-ups and I have not verified it against the leaderboard directly, so treat the exact ranks as approximate. The magnitude of the effect is the point, and it is corroborated by Trivedy's team independently moving an agent from Top 30 to Top 5 by changing only the harness.

There is a mechanism for this, and it is not "custom harnesses are just better":

Models get post-training coupled to the harness they were trained against. Moving them into a different harness — with better tools for your codebase, a tighter prompt, and sharper back-pressure — can unlock capability the original harness was leaving on the floor.Addy Osmani, paraphrasing the mechanism
What this breaks

Every claim of the form "model X scores N on benchmark B" is really "model X in harness H scores N on B". If H is unspecified, the number is not reproducible and comparisons across labs are not apples to apples. This is not a minor caveat — the harness effect above is larger than the gap between many adjacent model releases.

Section 2The HarnessCard

The preprint by He et al. (Preprints.org 202603.1756) argues that harness configuration should be reported alongside results as a matter of course, and proposes a standard disclosure. Their required fields:

FieldWhat it captures
Model + versionExact checkpoint, not "Claude"
Tool inventory & permissionsWhat the agent could do, and what was gated
Context policyCompaction, offloading, retrieval, window management
State / memory designWhat persists, in what format, across what boundary
Loop & stop conditionsIteration structure and every termination criterion
Feedback stackTests, graders, human checkpoints — what signals reached the agent
GovernanceSandboxing, approvals, provenance logging
Eval protocolTask set, number of runs, variance, outcome criteria, budget limits

I would treat this as a well-argued proposal rather than an adopted standard — it is a preprint, and adoption is currently near zero. But the fields are a good self-audit even if nobody else ever reads your card. If you cannot fill one in for your own system, you do not know your own system.

Section 3Capability framings

NVIDIA's developer blog offers a complementary lens: rather than listing components, enumerate the capabilities a harness provides and evaluate whether each is present and working. Their framing centres on things like environment setup and tool access, context management, planning and decomposition, verification and self-correction, error recovery, and observability.

The value is as a checklist against blind spots. Component lists tend to reflect what your framework happens to ship. Capability lists ask what the agent actually needs, which surfaces the gaps — most commonly error recovery and observability, which no framework makes you configure and which nothing forces you to notice are missing.

The structure to notice: each removed component maps to exactly one degraded column. That one-to-one mapping is the definition of load-bearing. Remove permissions, the destructive command runs. Remove back-pressure, the agent ships broken work. Remove either context control, the window inflates 3.5–5.5x. Remove everything, all three fail and context is 21.7x the baseline.

A component that changes no column under ablation is not load-bearing. It is cost.

Four rules that make this measurement rather than vibes

  1. Fix the model. An ablation across different models measures nothing. Pin the exact checkpoint.
  2. Run n > 1. Real agent runs are non-deterministic. A single run is an anecdote. Report variance, not just the mean — and if variance swamps your effect, you have not found an effect.
  3. Report cost alongside outcome. +2% at 20x cost and +2% for free are different decisions. Anthropic's 6hr/$200 versus 20min/$9 comparison is the model for this.
  4. Re-run on every model upgrade. Components expire. Context resets were essential on Sonnet 4.5 and dead weight on Opus 4.5.
On the fake model

The lab uses a scripted model, which makes the table above perfectly reproducible and n=1 sufficient. That is the right instrument for teaching the method, because it isolates harness behaviour completely. When you run this against a real model on real tasks, rule 2 becomes binding and the table gets error bars. Do not skip that step and do not report the deterministic version as if it were the real one.

Section 5What to measure

Outcome metrics alone are too coarse to debug a harness. Pair them with process metrics:

OutcomeProcess
Task success rateTool calls per task; error rate per tool
Cost per completed taskContext size over time; truncation count
Wall clock to completionSteps to first verification signal
Human interventions requiredDenials, hook fires, recovery attempts
Regressions introducedPremature-completion rate

The process column is what tells you why a number moved. A success-rate drop with a simultaneous spike in truncations points at Module 03. A drop with unchanged process metrics points at the model or the task set.

Exercises
  1. Fill in a HarnessCard for a system you actually use. Which field is hardest, and what does that say about what you have not designed deliberately?
  2. Add a needle-survival column (from Module 03) to the ablation table. Does the context-policy row now show a cost the current table hides?
  3. Find a published agent benchmark claim. What harness details are disclosed? Could you reproduce it?
  4. Instrument one process metric on your real setup and watch it for a week. Most people discover something they were wrong about.
