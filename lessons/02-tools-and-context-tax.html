Harness Engineering · Module 02

Tools, bash, and the context tax

Every tool you add is charged against the model's attention on every turn, before it reads your task. This module counts that cost in characters, then gives you the two moves that reduce it: bash instead of bespoke tools, and CLI instead of MCP.

Section 1The filesystem is the foundational primitive

Trivedy's derivation starts here and it is the right place. Models operate only on what is in context. Before filesystems, that meant copy-pasting into a chat window — clunky for a human and impossible for an autonomous agent. The solution was available and already deeply represented in the training data:

The world was already using filesystems to do work, so models were naturally trained on billions of tokens of how to use them.Vivek Trivedy

What the filesystem unlocks, in order of how much it matters:

  • Offloading. Work can be written down instead of held in the window. This is the mechanism behind every context strategy in Module 03.
  • Persistence. State outlasts a session. This is what makes Module 04's handoff possible at all.
  • Collaboration. Multiple agents and humans coordinate through shared files. Anthropic's three-agent harness passes everything this way — one agent writes a file, another reads it and responds in the same file or a new one.
  • Versioning, once you add git: track progress, roll back errors, branch experiments.

Nearly every other harness primitive ends up pointing at the filesystem for something. If you are designing from scratch, give the agent a workspace before you give it anything else.

Run it
terminal
python3 lab/w02_tools.py

Section 1 writes a file, verifies it with wc -l, and reads it back — the write/verify/read cycle that every coding agent runs thousands of times. Note that verification uses a different tool than the write did. An agent that verifies with the same mechanism it wrote with is not verifying.

Section 2Bash: the tool that removes the need for tools

A harness can only execute the tools it has logic for. That gives you two strategies. You can try to anticipate every action the agent might need and build a tool for each — an infinite and losing task. Or you can give it bash.

It's the difference between teaching someone to use a single kitchen gadget and handing them a kitchen.Addy Osmani, on bash + code execution

The model designs its own tools on the fly by writing code, rather than being confined to a fixed inventory. Willison's observation is that most tasks collapse into a few well-chosen CLI invocations anyway, and models are extremely good at shell commands because the training data is saturated with them.

Harnesses still ship focused tools. But bash plus code execution has become the default general-purpose strategy, and if you find yourself writing your fifteenth bespoke tool, ask whether a CLI already does it.

The allow-list, and why refusals must be readable

lab/harness_lab.py · make_bash_tool
def bash(cmd, **_):
    prog = shlex.split(cmd)[0] if cmd.strip() else ""
    if prog not in allow:
        return f"BLOCKED: '{prog}' is not on the allow-list {sorted(allow)}"
    ...

Section 2 of the walkthrough sends rm -rf / through this. It is refused, and — the part that matters — the refusal comes back as a string the model reads, so it adapts and continues with the safe command. Compare to a silent failure, where the agent has no idea what happened and retries in circles.

This is the same principle as error-as-observation from Module 01. State it once, generally: a harness control that is enforced but not legible produces a confused agent; a control that is legible produces an adaptive one.

Section 3Counting the tool tax

Here is the measurement almost nobody makes. Tool descriptions and schemas are injected into context on every turn. Real numbers from the walkthrough, using deliberately ordinary descriptions of about 120 characters each:

real output · lab/w02_tools.py
 tools    context chars    ~tokens
     4              864        216
    12            2,598        649
    30            6,540      1,635
    60           13,110      3,277
   120           26,310      6,577
Read this carefully

120 tools is roughly what you get from six or seven chatty MCP servers. That is ~6,600 tokens spent before the agent reads your task, on every turn, charged against the same attention budget the actual work needs. The character counts above are exact for the synthetic tools in the script; treat the token figures as a ÷4 approximation. Your real numbers depend on how verbose your descriptions are — which is the point. Go measure yours.

This is the mechanism behind the widely-reported "too many MCP servers makes the agent dumber". It is not folklore and it is not mysterious. It is arithmetic plus context rot: you are spending window on things the current task does not need, and everything you spend degrades attention on everything else.

Progressive disclosure

The counter-pattern, and the reason skills exist as a harness primitive:

Skills address the issue of too many tools or MCP servers loaded into context on agent start, which degrades performance before the agent can start working. Skills are a harness-level primitive that solve this via progressive disclosure.Vivek Trivedy

Ship a short index — name and one-line description. Load the full instructions, schemas, and examples only when the task actually calls for that skill. The agent did not choose to have every tool's front-matter loaded at startup; the harness can choose not to do that to it.

Section 4CLI over MCP, when the CLI is in the training data

HumanLayer's field report is the strongest practical guidance available on this, and it reduces to a decision rule:

QuestionAnswer
Does a well-known CLI already do this? (git, gh, docker, psql, jq, kubectl)Use the CLI. Zero tool-description tax, composable with pipes and grep, and the model already knows the syntax from pretraining.
Is it bespoke to your system?Write a thin tool. Return the smallest useful payload — not the full API response.

Their reported result: they replaced the Linear MCP server with a short CLI section in CLAUDE.md and got better outcomes for less context. The mechanism is not subtle — an MCP server pays a per-turn description cost for capability the model could have invoked through a binary it already understands.

Where this rule stops applying

MCP earns its cost when the tool needs to be discoverable by an agent you did not configure, when it needs auth the CLI cannot carry safely, or when there is no CLI and you would be shipping one just for this. The rule is "prefer the CLI when the CLI is already known", not "MCP is bad".

Tool output is the other half of the tax

Tool descriptions cost on every turn. Tool outputs cost once but arrive much larger. A 2,000-line log file, a full API response, a passing test suite — these flood the window with tokens that carry almost no signal. Two mitigations, both harness-level:

  • Truncate with a pointer. Keep head and tail above a threshold; offload the middle to a file the agent can read on demand. That is max_tool_chars in the lab harness.
  • Design the payload. Do not return what the API gave you. Return what the agent needs. Module 05 takes this to its conclusion: on success, return nothing at all.
Exercises
  1. Add a tool with a 2,000-character description. Re-run section 3. How many such tools before you have spent 10% of a 200k window on descriptions alone?
  2. Count your own. Dump your actual tool inventory to JSON and measure it. Most people are surprised.
  3. Add git to the allow-list. Does the harness now permit git push --force? Write the approve() callback that permits git but refuses force-push and refuses pushes to main.
  4. Take your three least-used tools. For each, write the one-line CLI invocation that replaces it. If you can, delete the tool.
