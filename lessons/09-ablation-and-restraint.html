Harness Engineering · Module 09

The discipline of deleting

Every harness component encodes an assumption about what the model cannot do. Assumptions expire, silently, on a schedule set by someone else's release calendar. This module is about the only reliable way to find the expired ones — and the capstone that makes you do it.

Walkthrough + capstone + quizlab/w08_ablation.py60 minCompiled by Premansh Panigrahi

Section 1The central claim

Every component in a harness encodes an assumption about what the model can't do on its own, and those assumptions are worth stress testing — both because they may be incorrect, and because they can quickly go stale as models improve.Anthropic, Harness design for long-running application development

Read that as a maintenance obligation. Your harness is a set of bets about model weakness. Some were wrong when you made them. Others were right and have since expired. Neither kind announces itself, because a harness component that has become useless still works — it just costs you tokens, latency, and complexity for nothing.

The documented examples from this course:

ComponentAssumption it encodedFate
Context resetsThe model gets context anxiety and wraps up earlyDropped on Opus 4.5 — behaviour gone from the model
Sprint decompositionThe model cannot chunk a large build itselfRemoved on Opus 4.6 — handled natively
Per-sprint evaluatorThe model ships plausible-looking broken codeReduced to a single end pass; still earns its cost only at the capability edge
PlannerThe generator under-scopes from a bare promptKept — the failure is still live

Three of four expired within roughly two model generations. That is the half-life you are designing against.

Section 2The method

Anthropic tried the intuitive approach first and it failed instructively. They cut the harness back radically and introduced new ideas at the same time. They could not replicate the original performance — and worse:

It also became difficult to tell which pieces of the harness design were actually load-bearing, and in what ways.Anthropic

Changing many variables at once destroys your ability to attribute the result. They restarted with the boring method: remove one component at a time, measure, decide.

Section 3The counter-argument, taken seriously

There is a real position that most harness engineering is a temporary patch on model immaturity, and that elaborate scaffolding is what the bitter lesson warns against. Hugo Bowne-Anderson argues a version of this: teams over-engineer harnesses, then find each model release invalidates the work.

The strong form of the argument does not survive contact with Module 02 — a model with no filesystem, no tool execution, and no sandbox is not an agent no matter how capable it gets. Some harness is definitional.

  • Harness complexity that compensates for a model weakness is temporary. Budget for its deletion.
  • Harness complexity that provides a capability the model structurally lacks — state, execution, verification against ground truth, isolation — is durable.
  • When you cannot tell which kind you are building, you are building the temporary kind.
The failure mode this module exists to prevent

A harness that only accumulates. Every incident adds a rule to AGENTS.md, a hook, a check. Nothing is ever removed, because removal feels risky and nobody can prove the component is dead. Eighteen months later you are paying thousands of tokens per turn for constraints against failure modes that vanished three model versions ago — and the accumulated context is itself degrading performance. The ratchet only works if it turns both ways.

Section 4Capstone

Everything in this course, applied once, end to end. Budget two to four hours.

Part 1 — Build

  • Tools scoped to the task, with descriptions you have actually counted (Module 02)
  • A context policy — offload rather than compaction unless you can justify otherwise (Module 03)
  • A handoff artifact with machine-checkable completion (Module 04)
  • Verification: silent on success, actionable on failure, wired to a hook (Module 05)
  • Stop conditions: steps, wall clock, cost (Module 01)
  • A permission gate on anything irreversible (Module 07)
  • A trace you can read afterwards (Module 01)

Part 2 — Card

Fill in a HarnessCard (Module 08). Every field. The ones you struggle with are the parts you did not design.

Part 3 — Ablate

Remove one component at a time. For each, record: what degraded, by how much, at what cost. Fix the model. Run n > 1 and report variance. Build the table.

Part 4 — Delete

Remove everything the table shows is not load-bearing. This is the part that will feel wrong and is the point of the exercise. Re-run and confirm nothing broke.

Part 5 — Write it down

One page: what you kept, what you deleted, what surprised you. Date it and name the model version.

Section 5Check your understanding

Quiz · Module 09

Why did Anthropic's first "cut the harness back radically" attempt fail?
Why: Changing several things simultaneously destroys attribution. The one-at-a-time ablation is what makes "load-bearing" visible — each removal degrades exactly one column.
The "ratchet only works if it turns both ways" warning means…
Why: If you only ever add rules and never remove dead ones, you pay tokens for constraints against failure modes that vanished. Deletion is the other direction the ratchet must turn.
Which kind of harness complexity is DURABLE, per the bitter-lesson argument?
Why: A model can't grow a filesystem or a sandbox by getting smarter. Those capabilities are definitional and survive model upgrades. Weakness-compensating complexity is what expires.
In the capstone, Part 4 ("delete") is described as…
Why: The whole course builds to this: build, card, ablate, then delete what the table shows is cost. It feels wrong because accumulation is the default — which is exactly why it matters.
