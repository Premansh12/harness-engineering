Harness Engineering · Module 01

The loop is the agent

An agent is twelve lines of code. Everything hard about agents is a failure mode of those twelve lines, and every harness feature you will ever build is a patch on one of them. Start by writing it, then break it deliberately.

Walkthroughlab/w01_loop.py40 minCompiled by Premansh Panigrahi

Section 1The whole idea

Simon Willison's definition is the most compressed one available and it is correct: an agent is a system that runs tools in a loop to achieve a goal. Written out:

lab/w01_loop.py · the core
def minimal_loop(model, tools, task, max_steps=10):
    messages = [{"role": "user", "content": task}]
    for _ in range(max_steps):
        out = model.complete(messages)
        if out["type"] == "text":
            return out["text"]
        result = tools[out["name"]](**out.get("args", {}))
        messages.append({"role": "assistant", "content": f"call {out['name']}"})
        messages.append({"role": "tool", "content": str(result)})
    return "STOPPED: step budget exhausted"

That is a ReAct loop: reason, act, observe, repeat. It is genuinely all there is to the control flow. If you have been treating agent frameworks as containing some essential complexity, this is the moment to notice that they do not.

Run it

Four sections. The first runs the loop above on (17+25)*3 and reports three model calls for one arithmetic question — a useful reminder that every tool call is a full round trip you are paying for in latency and tokens.

Section 2Break it: the loop that never stops

Feed the loop a model that always returns a tool call and never returns text. With max_steps, you get a clean stop. Without it, the process runs until something external kills it — your budget, your patience, or your rate limit.

This sounds too obvious to dwell on, and yet the interesting part is what the correct behaviour is. When the budget is exhausted, the loop in the walkthrough does not raise. It returns a status:

{"status": "budget_exhausted", "answer": None, "steps": 12}

An exception is the wrong shape here. Hitting a budget ceiling is not an error — it is one of the expected terminal states of an agent run, alongside success and refusal. Anything upstream needs to distinguish "the agent finished and was wrong" from "the agent never finished", and an exception collapses that distinction.

The stop conditions worth having

  • Step budget — hard ceiling on iterations. Always. Non-negotiable.
  • Wall clock — for anything long-running. A step budget does not bound a step that hangs.
  • Cost ceiling — dollars, tracked live. The only one that maps to the thing you actually care about.
  • No-progress detection — same tool, same args, N times running. The agent is stuck and does not know it.
  • Goal satisfied — evaluated by the harness, never by asking the agent. See Module 06.
Never ask the agent whether it is done

The single most reliable way to get a false completion is to ask the model "is the task complete?" It will say yes. Anthropic documents this as a first-class failure mode in long-running work, and it is the mechanism behind Module 04's shift-change problem. Termination is a harness decision, evaluated against artifacts outside the model's control.

Section 3Break it: one bad tool kills the run

Section 3 of the walkthrough gives the loop a tool that raises ValueError("upstream 503"). The raw twelve-line loop propagates it and the run dies. In a real system that is a six-hour job lost to a transient network blip on step 400.

The fix is three lines, and the interesting thing is what those three lines do:

lab/harness_lab.py · Harness._dispatch
try:
    return str(tool.fn(**args))
except Exception as exc:
    self.trace.add("tool_error", name=name, error=repr(exc))
    return f"ERROR from {name}: {exc!r}"

The exception is converted into an observation. Not swallowed, not logged and skipped — turned into a string and handed back to the model as the result of its action. Here is the actual trace from section 4:

real output

[ 0.000] tool  fetch({'url': 'https://x'})
[ 0.000] tool_error {'name': 'fetch', 'error': "ValueError('upstream 503')"}
[ 0.000]   ->  ERROR from fetch: ValueError('upstream 503')
[ 0.000] tool  add({'a': 2, 'b': 2})
[ 0.000]   ->  4
[ 0.000] say   fetch failed, but 2+2=4 so I proceeded.

The agent routed around a failure it was told about in plain text. It did not need a retry framework, a circuit breaker, or a special error-handling prompt. It needed the error to arrive somewhere it could read it.

The recovery path is harness code. The model contributed nothing to it — except the ability to read English.The general principle

This generalises further than error handling. Almost every harness control works better when it is legible to the agent rather than merely enforced against it. A blocked command that returns "BLOCKED: rm is not on the allow-list" produces an agent that tries something else. A blocked command that silently returns empty produces an agent that loops in confusion. Module 07 returns to this.

Section 4What the Harness class adds

The Harness class in lab/harness_lab.py is the twelve-line loop plus every feature this course covers, each one switchable. Read the constructor as a checklist of design decisions:

lab/harness_lab.py
Harness(
    model,
    tools,
    system="You are a coding agent.",
    max_steps=12,            # stop condition — Module 01
    max_tool_chars=1200,     # context policy — Module 03
    approve=None,            # permission gate — Module 07
    hooks=None,              # deterministic control — Module 05
    context_policy=None,     # compaction / offload — Module 03
    trace=None,              # observability — this module
)

Every argument is a lever, and in Module 09 you will turn each one off and measure what breaks. That is the payoff for keeping them explicit rather than baking them in.

Observability is not optional

The Trace object is the least glamorous component here and the one you will use most. A harness you cannot inspect is a harness you cannot debug, and agent runs fail in ways that are invisible from the outside — the agent that "worked" but silently truncated a tool result, the agent that hit its step budget one call short of finishing, the agent that called the same tool eleven times.

The minimum viable trace records: every tool call with arguments, every result (truncated for readability), every model text turn, and every intervention the harness made — denials, truncations, hook injections, errors. The report() method rolls that into six numbers. Get in the habit of reading them.

Why a fake model is the right instrument

Everything in this course runs against a scripted FakeModel. That is not a limitation of the teaching setup — it is the correct experimental design. You are studying harness behaviour, so the model must be held perfectly constant. A real model introduces run-to-run variance that swamps the effect you are trying to see, and costs money to observe. Script the trajectory, isolate the harness, measure cleanly. Module 09 discusses what changes when you switch to a real model, and what does not.

Exercises
  1. Set max_steps=1 in section 4 of the walkthrough. What status comes back? Argue why returning a status is more correct than raising.
  2. Add a tool that returns 50,000 characters. Watch truncations go to 1 in the report, then set max_tool_chars=10**9 and watch context_chars explode. That is Module 03 previewed in one line.
  3. Implement no-progress detection: if the same tool is called with identical arguments three times running, stop with status "stuck". Roughly six lines in Harness.run.
  4. Harder: make the step budget adaptive. Start at 10; if the last three tool calls all succeeded, grant 5 more, up to a hard ceiling of 40. Is this a good idea? Argue both sides — under what failure mode does it make things worse?
