Harness Engineering · Module 01

The loop is the agent

Everything else in a harness is support for one thing: a loop that calls the model, runs what it asks for, feeds the result back, and decides whether to stop. Get the loop wrong and no amount of tooling saves you. Build it in twelve lines, then break it three ways.

Reading + walkthrough + quizlab/w01_loop.py45 minCompiled by Premansh Panigrahi

Section 1What an agent is, in one sentence

An agent is a model wrapped in a loop. The model alone generates text. The loop is what lets it act: call a tool, observe the result, decide the next step, and stop when the job is done. Strip the loop and you have a chatbot. Add the loop and you have something that can complete a task over many steps without a human in the middle of each one.

This is the definitional claim of the whole field, and it is worth sitting with because it demotes the model. The model is necessary but not sufficient. The thing that makes the system an agent is the harness around it — and the loop is the first layer of that harness.

Section 2The loop, in twelve lines

Here is the entire agent. No tools, no context policy, no safety — just the irreducible core:

def agent(model, task, max_steps=10):
    msgs = [{"role": "user", "content": task}]
    for step in range(max_steps):
        out = model.complete(msgs)            # 1. ask the model
        if out["type"] == "text":             # 2. is it done?
            return out["text"]                #    yes -> stop
        if out["type"] == "tool_call":        # 3. or does it want to act?
            result = run_tool(out["name"], out["args"])
            msgs.append(out)                  # 4. remember what it asked
            msgs.append({"role": "tool",      # 5. feed result back
                         "content": result})
    return "gave up after " + str(max_steps) + " steps"

Five operations, repeated: ask → decide → act → observe → append. That is the whole discipline. Every component added later — tool routing, context windows, verification, permissions — exists to keep this loop correct over a long horizon. None of them change its shape.

The irreducible loop: ask → decide → act → observe → append. Everything else wraps this.

Section 4Why the loop's failures are the whole problem

Notice that none of the three breaks is a model failure. The model did exactly what it was asked. The failures are all in the harness: a missing bound, a missing memory write, a missing stop test. This is the recurring shape of the entire field — capability problems that are actually scaffolding problems. HumanLayer puts the blunt version on record: "It's not a model problem, it's a configuration problem."

Concretely, the loop needs four things decided before it touches a real task:

1Stop conditions
Steps, wall-clock, cost, or an explicit completion signal. Without at least one hard bound, a stuck agent costs you money forever and produces nothing. Module 09 shows a real ablation where removing the step cap let a bare loop run 21.7x the context of the full harness.
2Error recovery
A tool fails. Does the loop pass the error back to the model and let it retry, or does it crash? The recovery path is a harness decision, and a bad one turns a recoverable error into a dead agent.
3Append discipline
What goes into history and in what shape. Drop the tool result and the agent amnesias; keep everything and you overflow the context window (Module 03). The loop's memory policy is its second-most important decision after stopping.
4Who decides "done"
The model is a poor judge of its own completion (Module 05). The loop should evaluate completion with something the agent cannot grade — a test, a checker, a human gate.
