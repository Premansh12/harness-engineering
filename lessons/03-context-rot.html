Harness Engineering · Module 03

Context rot

Agent performance degrades as the window fills — not at the limit, but well before it. Three policies, one trajectory, and a needle test that shows exactly what each one destroys. The difference between reducing context and losing it is the whole lesson.

Walkthroughlab/w03_context.py50 minCompiled by Premansh Panigrahi

Section 1The phenomenon

Context rot is the observation that models get worse at reasoning and completing tasks as their context window fills up. Not "they error at the limit" — they degrade continuously, long before it.

This is the constraint that shapes more harness design than any other, and the reason is architectural. Attention is finite and distributed across everything present. Every token you add competes with every other token. A 200k window is not 200k of usable working memory; it is 200k of capacity across which a fixed attention budget gets thinner.

Context is a precious and scarce resource, so harnesses need strategies to manage it. Harnesses today are largely delivery mechanisms for good context engineering.Vivek Trivedy

A second and stranger effect compounds it. Anthropic documents context anxiety: some models begin wrapping up work prematurely as they approach what they believe is their context limit. The model's estimate of its remaining room changes its behaviour, independently of whether it is actually running out. Sonnet 4.5 exhibited this strongly enough that compaction alone was insufficient for long tasks.

Section 3The measurement

Read the rows honestly, including the one that is inconvenient.

None — append forever

The needle is present because nothing was discarded. This is also the most expensive run and it grows without bound. And note what "present" does not buy you: on a real model, recall degrades long before the window is full. The fact that a token is in context does not mean the model will use it. Doing nothing is not a safe default; it is an unbounded one.

Compaction — cheapest, and destructive

Context drops by 75%. The needle is gone, irreversibly. The problem is structural rather than a tuning failure: at compaction time you cannot know which tokens turn N+10 will need. Any summarizer, however good, is making an irreversible bet under uncertainty.

Compaction is still the right tool sometimes — it is what keeps a single continuous session alive, and it preserves conversational flow in a way a reset does not. Just be clear that it is lossy and that the loss is silent.

Offload — same cost, recoverable

Identical context savings. The needle also left the window — look at the in ctx? column, it says no. The difference is the last column: the dropped history was written to _ws03/offload/history-01.log and the note left in context says where. The agent can go get it.

Reducing what the model sees is cheap. Destroying what the model could ask for is the expensive mistake — and compaction makes it silently.The distinction this module exists for

This is the same argument Anthropic makes for the session log living outside the context window in Managed Agents: the session is an append-only event log, the context window is a view onto it, and because the log is authoritative, compaction becomes reversible. You can recompute a different view. That is a considerably stronger position than summarize-and-pray.

Section 4The three standard techniques

Compaction

When the window approaches full, summarize older turns in place. The alternative is an API error, which is not an acceptable production behaviour, so every serious harness has some version of this. Design questions: what threshold, how many recent turns to keep verbatim, and whether the summary is generated by a model call or assembled structurally.

Tool-call offloading

Large tool outputs clutter the window without adding signal. Keep the head and tail above a token threshold, write the full output to the filesystem, tell the agent where it went.

lab/harness_lab.py · Harness.run
if len(result) > self.max_tool_chars:
    kept = self.max_tool_chars // 2
    result = (result[:kept]
              + f"\n… [{len(result) - self.max_tool_chars} chars offloaded] …\n"
              + result[-kept:])

Head and tail specifically, because for logs and stack traces the signal is concentrated at both ends — the command that ran, and the error it produced.

Progressive disclosure

Covered in Module 02. Front-matter only at startup; full instructions on demand. This is the select move, and it is the cheapest of the three because it prevents the cost rather than mitigating it.

SituationReach for

Information you might need later but not nowwrite it to a file, keep a pointer

The mistake to avoid

Reaching for compaction as a general-purpose solution because it is the one every framework ships. It is the only one of the four that destroys information, and it is usually possible to write first and compress second. Ask "where does this go when it leaves the window?" before you ask "how do I shrink it?"

Exercises
  1. Set keep_last=1 in the compaction policy. At what point does the agent lose the thread of its own task, not merely the needle?
  2. Write a reduce policy that keeps only the first and last tool result and drops the middle entirely. Compare its recoverability to offload. Which of the four moves is it?
  3. Classify each of the three policies into write / select / compress / isolate. Which move has no representative in this walkthrough, and which module covers it?
  4. Harder: make the offload policy selective — keep any message matching a configurable importance pattern in context, offload the rest. Now argue why this is dangerous. (Hint: you are back to guessing what turn N+10 needs, but with worse recall than a summarizer.)
