The H0–H3 maturity ladder

Zhong & Zhu's "AI Harness Engineering" (arXiv:2605.13357) formalizes the harness as a runtime substrate and proposes an eleven-responsibility model plus a four-level maturity ladder. The ladder is the most useful single idea in the research literature for judging how serious a harness is.

Section 1The core reframing

Software-engineering capability emerges from a model-harness-environment system, in which a runtime substrate — the harness — mediates how a foundation-model agent observes a project, acts on it, receives feedback, and establishes that a change is complete.Zhong & Zhu, AI Harness Engineering (arXiv:2605.13357)

The paper's central move is to relocate the explanatory locus. The dominant story says "models aren't capable enough." Zhong & Zhu say the gap is often in the harness — the runtime that mediates observation, action, feedback, and completion. They formalize eleven component responsibilities:

Section 2The ladder

The paper operationalizes the harness through a four-level ladder (H0–H3) that "progressively exposes runtime support to the agent." Click each level to expand.

H0
Bare agent
The model plus a minimal loop, no runtime support. Produces only a final patch. No observability, no verification, no memory beyond the window. This is where most "just prompt the model" attempts live — and where the capability gap looks largest, because nothing mediates the model's interaction with the project.
H1
Tool-augmented
Adds tool access and basic context selection. The agent can act on the project and see relevant files. Still no structured verification or failure attribution — so when it fails, you get a broken patch and little signal about why.
H2
Verifiable
Adds verification and failure attribution. The agent now produces reproduction logs and a structured verification report. You can tell whether a change is correct, not just whether it exists. This is the level where "completion" stops being self-asserted (Module 05).
H3
Auditable / attributed
Adds observability, intervention recording, and entropy auditing. Each run becomes an episode package: patch + reproduction log + failure attribution + deterministic requirement check + structured verification. The change is verifiably correct, attributed to causes, and maintainable. This is the paper's target and the capstone's destination (Module 16/17).

The paper validates this on a controlled task: lower levels produce "only a final patch," higher levels produce "reproduction logs, failure attributions, deterministic requirement checks, and structured verification reports." The evidence structure varies systematically with harness level — which is exactly the confound Module 08 warns about, made measurable.

Section 3Trace-based evaluation

The paper's evaluation protocol "converts each agent run into an auditable episode package." That is the research version of the trace we touched in Module 12/14: every run is a record you can replay and attribute. This is also where it connects to the self-evolving work (Module 15) — those systems consume exactly these episode packages as training signal.

Section 4Check your understanding

Quiz · Module 11

Zhong & Zhu relocate the "agents aren't capable enough" gap to…
Why: They argue capability emerges from a model-harness-environment system; the under-built part is usually the harness, not the model weights.
On the H-ladder, which level first adds verification and failure attribution?
Why: H0 = final patch only; H1 = tools + context; H2 = adds verification and failure attribution so completion is no longer self-asserted; H3 = adds observability and audit.
The "episode package" evaluation protocol matters because…
Why: Converting a run into an episode package (patch + logs + attribution + verification) makes the confound measurable and doubles as the training data self-evolving harnesses consume.
The paper's eleven responsibilities (task spec, context, tools, memory, state, observability, attribution, verification, permissions, entropy audit, intervention) are best understood as…
Why: Each responsibility maps to a module in Part I. The research paper generalizes the practice into a responsibility model — useful as a checklist of what a serious harness must do.
