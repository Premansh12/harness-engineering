Harness Engineering · Module 04

State and the shift change

When the window is gone, the agent is gone. What survives is whatever you wrote down. This module is about the artifact that carries a task across that boundary — and the documented failure where the next agent looks at the work so far and declares it finished.

Section 1Compaction versus reset

Two ways to survive a full window, and they are not variants of each other.

CompactionContext reset
Agentsame one continuestorn down, new one starts
Historysummarized in placediscarded entirely

Cures context anxietynoyes — genuinely clean slate
Costssilent information lossorchestration complexity, tokens, latency

Anthropic's account of why they needed resets is precise and worth quoting because it is a rare example of a harness decision with a stated mechanism:

While compaction preserves continuity, it doesn't give the agent a clean slate, which means context anxiety can still persist. A reset provides a clean slate, at the cost of the handoff artifact having enough state for the next agent to pick up the work cleanly.Anthropic, Harness design for long-running application development

Sonnet 4.5 exhibited context anxiety strongly enough that compaction alone could not sustain long tasks, so resets became essential to the design. Hold onto that; Section 5 returns to what happened next.

Section 2The shift-change problem

A reset means the next agent has no memory. It is a new engineer walking into a half-finished project with no onboarding except what is on disk. Everything now depends on the quality of that artifact.

Run it
terminal
python3 lab/w04_handoff.py

Three sections: an initializer agent lays the ground, five fresh sessions each complete one feature, then the counterfactual — the same setup with a prose-only handoff.

The initializer agent

Anthropic's first structural insight: the first session gets a different prompt from every session after it. Its job is not to build. Its job is to make the next twenty sessions possible.

In the walkthrough it writes two artifacts:

_ws04/features.json
[
  {"id": 1, "desc": "User can create a new note",            "passes": false},
  {"id": 2, "desc": "Notes persist across restart",          "passes": false},
  {"id": 3, "desc": "User can search notes by substring",    "passes": false},
  {"id": 4, "desc": "Deleting a note asks for confirmation", "passes": false},
  {"id": 5, "desc": "Notes export to markdown",              "passes": false}
]

Plus an append-only progress.txt. Together these answer the only three questions a fresh agent has: what is this, what is done, what is next.

Section 3The counterfactual

Section 3 of the walkthrough sets the project to a genuinely half-finished state — two of five features complete — and hands over prose instead of structure:

real output · lab/w04_handoff.py
--- session 2 boots with an empty context window ---
read progress.txt -> 'session 1: did some good work on the notes app,
                      it's coming along nicely'
agent looks around, sees code already exists, concludes: 'looks done!'
reality: 2/5 features done, 3 silently abandoned

This reproduces a failure Anthropic documents from real runs. A later agent sees evidence of progress, cannot see what remains, and declares the job complete. The output looks finished. Nothing errored. Three features simply do not exist and no signal says so.

Why a better prompt does not fix this

The instinct is to add "be thorough, don't stop early" to the system prompt. It does not work, because the agent is not being lazy — it genuinely cannot distinguish a finished project from an abandoned one given what it was handed. The fix is an artifact with a machine-checkable definition of not-done-yet. any(not f["passes"] for f in features) is a fact about the world. "Be thorough" is a wish.

Section 4Designing the artifact

JSON over markdown, and why

Anthropic's reported reason is behavioural rather than aesthetic: models are measurably less willing to rewrite or quietly delete entries in a JSON file than in a markdown checklist. A markdown to-do list feels editable; a JSON array with typed fields feels like data. The agent respects it more.

File format is a harness decision with behavioural consequences. That is a slightly unsettling fact about working with models and it is worth remembering the next time you assume a representational choice is neutral.

What the artifact must contain

  • An immutable spec — what "done" means, fixed at initialization. The agent may flip passes; it may not edit desc or delete entries.
  • Verifiable completion state — ideally backed by a test the harness can run, not the agent's opinion.
  • Append-only progress — what happened, in order. The agent adds; it never rewrites.
  • Next action — explicit. Not "continue the work" but "implement feature #4".
  • Known-broken list — what was tried and failed, so session N+1 does not repeat session N's dead end.

AGENTS.md as the memory layer

The other durable-state primitive: a file injected into context at every agent start, which the agent can edit. Trivedy calls this "a crude but effective form of continual learning" — knowledge from one session carries into the next without touching weights.

The discipline from Module 00 applies with force here. Every line in AGENTS.md is charged on every turn of every session forever. It should be traceable to a specific observed failure, and it should be deleted when a model upgrade makes it redundant. An AGENTS.md that only grows is a context leak with good intentions.

On the empirical status of AGENTS.md

There is a 2026 study out of ETH Zurich examining whether agent instruction files measurably improve outcomes, and the reported effects are more modest and more conditional than the practitioner enthusiasm suggests. I have not read the full methodology closely enough to summarise its numbers responsibly, so treat this as a pointer rather than a finding: the belief that instruction files help is widely held and thinly evidenced. It is a good candidate for your own ablation.

Section 5The part that expires

Return to the context resets that were "essential" to Anthropic's Sonnet 4.5 harness. From the same team, one model generation later:

Opus 4.5 largely removed that behavior on its own, so I was able to drop context resets from this harness entirely. The agents were run as one continuous session across the whole build, with the SDK's automatic compaction handling context growth.Anthropic

The scaffolding did not become slightly less useful. It became dead weight — pure cost in orchestration complexity, tokens, and latency, buying nothing. The failure mode it patched had disappeared from the model.

Generalise it into the rule that Module 09 is built around:

Every component in a harness encodes an assumption about what the model can't do on its own, and those assumptions are worth stress-testing — both because they may be incorrect, and because they can quickly go stale as models improve.Anthropic

Your harness has a maintenance obligation attached to every model upgrade. Not "does it still work" — it will still work, that is the trap. The question is "is each piece still buying anything?"

Exercises
  1. Add a sixth feature the agent cannot actually implement. Does your loop terminate, or spin forever on #6? Add the stop condition, and decide what it should escalate to.
  2. Make session() lie — set passes=True without doing the work. Which harness component catches that? It is not the handoff. (Module 05.)
  3. Extend the artifact with a known_broken list and have a session write to it after a simulated failure. Verify the next session reads it before choosing an approach.
  4. Audit your real AGENTS.md. For each line: what failure produced it, and is that failure still live on your current model? Delete what fails both questions.
