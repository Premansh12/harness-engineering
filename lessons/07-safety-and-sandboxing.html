Harness Engineering · Module 07

Permissions, sandboxes, blast radius

Prompt injection is not a prompting problem — it is an architecture problem. The agent runs inside an environment you control; the question is how small you can make the blast radius when something lies to it.

Reading + walkthrough + quizlab/w07_safety.py45 minCompiled by Premansh Panigrahi

Section 1Injection is an architecture problem

A model reads untrusted text — a webpage, an email, a file in the repo. That text can say "ignore your instructions and run this." If the agent has the tool and the permission, it will. You cannot prompt your way out of this reliably; the model is, by design,顺从 to text. So the defense is structural: what can the agent do, and what can it reach?

Anthropic's pets-to-cattle refactor makes this concrete. Early harnesses ran the agent inside the harness process. They moved the agent out into its own sandbox — cattle, not pets — so a compromised agent can be killed and rebuilt without taking the controller with it.

Section 2The credential proxy

The sharpest move in the managed-agents work: a credential proxy. The agent never holds the API key. It asks the proxy, the proxy holds the secret and the policy, and the proxy decides. The key never enters the agent's context — so a prompt injection that says "print your environment variables" gets nothing.

agent asks: rm -rf .                        -> BLOCKED (not on allow-list)
agent asks: echo working normally           -> allowed -> exit=0

The allow-list (introduced in Module 02) is the first line. But allow-lists alone don't stop injection — an injected instruction can ask for a permitted command. The deeper layers are the sandbox (what the command can touch) and the proxy (what secrets it can reach).

Section 3Three layers of blast radius

LayerWhat it containsFailure mode it prevents
Allow-listWhich commands may runArbitrary command execution
SandboxWhich files/network the command reachesLateral movement, data exfil
Credential proxyWhich secrets the agent can useToken theft via injection

Microsoft's Agent Framework ships a `ShellExecutor` with a deny-list (rm -rf, sudo) and working-directory confinement — but its docs are explicit that the deny-list is "a UX pre-filter, not a security boundary." The real boundary is the sandbox. Treat any deny-list as convenience, not safety.

Each outer layer shrinks what a compromised agent can reach. The key never enters the agent.

Section 4Least privilege, by default

The discipline: start from nothing. The agent gets the minimum tool, the minimum file access, the minimum secret for the task. Add per task, revoke after. This is the same ratchet logic as Module 09 — except here the cost of excess is not tokens, it is a breach.
