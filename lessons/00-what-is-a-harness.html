Harness Engineering · Module 00

What a harness actually is

Before anything useful can be said about designing harnesses, the word has to stop meaning four different things. This module fixes the terminology, then gives you the stack you will spend the rest of the course filling in.

Reading25 minNo walkthroughCompiled by Premansh Panigrahi

Section 1The definition, and its problem

The working definition is a subtraction:

A harness is every piece of code, configuration, and execution logic that isn't the model itself. A raw model is not an agent. It becomes one once a harness gives it state, tool execution, feedback loops, and enforceable constraints. Vivek Trivedy, LangChain, March 2026

This is clean and it is also almost uselessly wide. "Everything that isn't the model" covers a system prompt and a Kubernetes cluster equally. Martin Fowler's site makes the same complaint and narrows it by bounded context: what counts as the harness depends on where you are standing.

Standing atModelHarness
A lab training a modelthe weightsthe RL environment, the scaffolding it was post-trained against
A vendor building Claude CodeClaudethe CLI, tools, system prompt, compaction, hooks
You, using Claude CodeClaude Code as a wholeAGENTS.md, skills, hooks, MCP config, CI checks, your review loop

Böckeler calls the third row the outer harness: the part the tool's users build for their own codebase. Part of the harness ships with the agent and you cannot change it; part of it is yours. Most practical harness engineering happens in the outer layer.

On the metaphor

Someone told Böckeler: "Have you ever tried to put a harness on the inside of a dog?" Nesting harnesses inside harnesses does stretch the word past breaking. Accept it as jargon that earns its keep by being useful, not by being apt.

Section 2Why a harness has to exist at all

Derive it from the model's actual capability surface rather than from what agent frameworks happen to ship. A model takes in tokens and emits tokens. That is the whole interface. Out of the box it cannot:

  • maintain durable state across interactions
  • execute code
  • access anything that postdates its training cutoff
  • set up an environment or install a dependency
  • observe the consequences of its own output

Every one of those is a harness feature. Even chat is a harness: a while-loop that accumulates messages. You have been using harnesses since your first API call; the discipline is just taking that layer seriously as an artifact you design rather than inherit.

The generative pattern Trivedy uses, and the one worth internalising:

Behaviour we want (or want to fix) → harness design that helps the model achieve it.The derivation rule

Read backwards, this is also a deletion rule. If you cannot name the behaviour a component exists to deliver, it should not be there. Module 09 turns that into a measurement.

Section 3The four-layer stack

Assembled from the LangChain anatomy, the Anthropic engineering posts, and Böckeler's control-theory framing, the components sort into four layers. The rest of the course is one module per cluster.

Layer 1 · Interface — what the model can touch

  • Tools and their descriptions; MCP servers; skills
  • Filesystem — workspace, durable state, collaboration surface
  • Bash / code execution — the general-purpose tool that removes the need to pre-build every other one
  • Sandbox — where that code runs, and what it can reach from there

Layer 2 · Context — what the model sees, and when

  • System prompt, AGENTS.md / CLAUDE.md, skill front-matter
  • Compaction, tool-output offloading, progressive disclosure
  • Retrieval and search; memory files

Layer 3 · Control — what happens between turns

  • The loop itself, and its stop conditions
  • Hooks and middleware — deterministic execution the model cannot skip
  • Permissions and approval gates
  • Orchestration — subagents, handoffs, model routing

Layer 4 · Feedback — how the system learns it was wrong

  • Verification: tests, linters, type checkers, builds
  • Inferential grading: LLM-as-judge, evaluator agents, code review
  • Observability: traces, cost and latency metering, logs
  • The human, positioned deliberately rather than by default

Section 4Feedforward and feedback

Böckeler's contribution is the cleanest organising axis in the field, borrowed from control theory. Everything in a harness is one of two things:

Guides (feedforward)Sensors (feedback)
Whenbefore the agent actsafter the agent acts
Jobraise P(correct on first attempt)let it self-correct
ExamplesAGENTS.md, skills, code mods, bootstrap scriptstests, linters, ArchUnit rules, review agents

Her warning about picking only one:

Separately, you get either an agent that keeps repeating the same mistakes, or an agent that encodes rules but never finds out whether they worked.Birgitta Böckeler, martinfowler.com

Crossed with a second axis — how the control executes:

ComputationalInferential
Runs onCPUGPU / a model call
Speedms to secondsseconds to minutes
Determinismreliable, repeatableprobabilistic, drifts
Costnegligible — run on every changereal — run selectively

The two-by-two is a design tool. Computational sensors are cheap enough to run on every edit and catch structural problems reliably — duplication, complexity, coverage gaps, architectural drift, style. Inferential sensors catch things requiring semantic judgment — semantically duplicated code, over-engineering, brute-force fixes — expensively and unreliably.

What neither catches

Böckeler is explicit about the residue: misdiagnosis of the actual problem, over-engineering, unnecessary features, and misunderstood instructions are caught by neither class reliably. And "correctness is outside any sensor's remit if the human didn't clearly specify what they wanted in the first place." No harness rescues an unspecified goal. This is the ceiling on autonomy and it is a human-side ceiling.

Section 5Three things this is not

Not prompt engineering

Prompt engineering optimises the string. Harness engineering designs the system that decides which strings exist, when they are assembled, what tools accompany them, and what happens to the output. The prompt is one component in Layer 2.

Not quite context engineering

Böckeler's formulation: "Context engineering provides us with the means to make guides and sensors available to the agent. Engineering a user harness for a coding agent is a specific form of context engineering." Trivedy inverts the containment — "harnesses today are largely delivery mechanisms for good context engineering." They are describing the same overlap from two sides. Practically: context engineering asks what goes in the window; harness engineering also asks what runs between turns, what the agent can touch, and when it stops. Layer 2 of four.

Not a framework

The most important structural claim in the field, from Addy Osmani:

The right harness for your codebase is shaped by your failure history. You can't download it.Addy Osmani, April 2026

You can download primitives. The specific set of constraints that makes an agent reliable in your repo is derived from mistakes you have actually watched it make. Which gives the field its central habit.

Section 6The ratchet

Osmani's one-line summary of the whole discipline:

Anytime you find an agent makes a mistake, you take the time to engineer a solution such that the agent never makes that mistake again.Addy Osmani

The habit underneath it is treating agent mistakes as permanent signals rather than bad runs to retry. His worked example: the agent ships a PR with a commented-out test.

  • AGENTS.md gains a line: never comment out tests; delete them or fix them.
  • The pre-commit hook greps the diff for .skip( and xit(.
  • The reviewer subagent gets commented-out tests as a blocking category.

Note that one failure produced controls at three different layers, with three different cost and reliability profiles. That is the shape of a mature response.

The discipline has a matching inverse, and it is the part people skip:

The two-sided rule

You only add a constraint when you have seen a real failure. You only remove it when a capable model has made it redundant. Every line in a good AGENTS.md should be traceable to a specific thing that went wrong. Every line that no longer maps to a live failure mode is context tax you are paying on every single turn.

Module 09 is entirely about the second half of that rule, because it is the half almost nobody does.

Section 7Harnessability

Not every codebase accepts a harness equally well. A strongly typed language gives you a type checker as a free sensor. Clear module boundaries afford architectural constraint rules. A framework that abstracts away detail reduces what the agent can get wrong.

Ned Letcher's term for this, quoted by Böckeler, is ambient affordances: "structural properties of the environment itself that make it legible, navigable, and tractable to agents operating within it."

The consequence is uncomfortable and worth sitting with. Greenfield teams can bake harnessability in from day one — the language, the architecture, and the test strategy all determine how governable the codebase will be later. Legacy teams face the inverse:

The harness is most needed where it is hardest to build.Birgitta Böckeler
Check yourself before moving on
  • Name the four layers and put one component of your current setup in each.
  • For each, say whether it is a guide or a sensor, and computational or inferential.
  • Find one line in your AGENTS.md that you cannot trace to a specific observed failure. That is your first deletion candidate.
  • Rate your main repo's harnessability. What ambient affordance is missing that would make the biggest difference?
