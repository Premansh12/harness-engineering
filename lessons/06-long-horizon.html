Harness Engineering · Module 06

Long horizons

Six-hour autonomous runs fail for reasons that have nothing to do with intelligence: the parent thread fills with noise, the agent stops early, and nobody outside the model is deciding when it is finished. Two mechanisms address this — subagents as a context firewall, and the loop that restarts from a clean window.

Section 1Three failure modes

Long-horizon autonomy is the hardest thing in this course to get right, and the failures are consistent across every source:

  • Early stopping. The agent decides it is done when it is not. Compounded by context anxiety (Module 03) and by prose handoffs (Module 04).
  • Poor decomposition. Given a large problem, the agent takes it on whole, produces something shallow, and cannot say which part failed.
  • Incoherence across windows. Work stretching past one context window loses the thread — not through forgetting exactly, but through the gradual degradation of Module 03.

The harness has to design around all three, and neither mechanism in this module fixes all of them alone.

Section 2Subagents as a context firewall

The isolate move from Module 03's taxonomy. Instead of running a token-heavy subtask inline, spawn a child agent with its own context window and take back only its conclusion.

Five research subtasks, each returning noisy results. Run inline, then delegated, with the parent's context measured both ways.

parent context after 5 searches:     16,169 chars
parent context after 5 delegations:     610 chars

parent context REDUCTION:              96.2%

Read all three numbers, not just the headline. The parent thread shrank by 96%. The total work did not get cheaper — the children collectively burned slightly more than the inline run, because each child re-pays for its own system prompt and task framing.

A subagent does not save tokens. It saves coherence — and on long tasks, coherence runs out before budget does.What the numbers actually say

A subagent is just another Harness with its own message list. There is no special machinery:

lab/w06_subagents.py
def spawn_subagent(q, **_):
    child = Harness(model_for(q), [Tool("search", "...", noisy_search)])
    out = child.run(f"research: {q}")
    return out["answer"]          # the parent sees only this

When to reach for one

Use a subagent whenDo not when
The subtask is independentThe parent needs the intermediate reasoning
It is token-heavyIt is a two-line lookup
Only the conclusion matters upstreamThe subtask must negotiate with the parent mid-flight

HumanLayer's tool-thrash warning

They tried carefully restricting which subagent got which tools — a sensible-sounding optimisation. It produced "tool thrash" and worse results: children lacking a tool they needed would work around its absence badly rather than failing cleanly. Their conclusion: give subagents a sane default toolbelt and stop micro-optimising. This is a good example of a harness intuition that measurement contradicted.

Section 3The Ralph loop

Named after the Simpsons character, and the crudest thing in this course that genuinely works:

while ! done; do
  agent "$SAME_PROMPT"
done

Same prompt, every iteration. Fresh context, every iteration. State lives on disk. The loop runs until an exit condition — evaluated outside the agent — is satisfied.

Why it works is exactly Module 03: a fresh context window is a reliable cure for incoherence, and restarting is cheaper than trying to keep a long session coherent. OpenAI's Codex team runs this shape in production; single runs go six hours, often overnight. Anthropic notes the developer community converged on the same pattern independently, using hooks or scripts to keep agents in continuous iteration cycles.

The three requirements

The loop is four lines of bash. Everything that makes it work is outside those lines:

  1. Durable state. Otherwise iteration N+1 redoes iteration N's work forever. This is Module 04's artifact, and the loop is the reason it has to be good.
  2. An exit condition evaluated outside the agent. Never ask the agent whether it is done — it will say yes. Check the artifact: any(not f["passes"] for f in features).
  3. A budget ceiling. Wall clock, dollars, or iterations. A loop whose exit condition is never satisfied is a loop that runs until you notice.
Harness engineering vs loop engineering

A distinction worth keeping. Harness engineering asks: what environment, tools, context, and state does the agent need? Loop engineering asks: what cycle keeps it on-goal, and when does it stop? The Ralph loop is almost entirely the second. Most published writing covers the first, which is part of why long-horizon work still feels like folklore.

Section 4Planner, generator, evaluator

Anthropic's three-agent architecture, with the specific gap each role closes:

AgentExists becauseDesign note
PlannerWithout it the generator under-scopes — it starts building immediately and produces a thinner product than a spec would have demanded.Takes a 1–4 sentence prompt, expands to a full spec. Deliberately high-level: product context and technical direction, not granular implementation.
GeneratorThe work.One feature at a time. Self-evaluates before handing off. Has git.
EvaluatorApps looked impressive and had real bugs when you actually used them.Drives the running app through Playwright like a user. Hard thresholds per criterion; below any one, the sprint fails.

The planner's restraint is the non-obvious part. They deliberately kept it away from granular technical detail, reasoning that errors in an upfront spec cascade into everything downstream. Constrain the deliverables, let the agents find the path.

Communication was entirely file-based: one agent writes, another reads and responds in that file or a new one. The filesystem as collaboration surface, from Module 02.

What happened when the model improved

The same arc as Module 04's context resets. On Opus 4.6, they removed the sprint construct entirely — decomposition the model now handled natively — and moved the evaluator to a single pass at the end. The planner stayed, because under-scoping was still a live failure. The evaluator stayed useful only at the edge of the generator's capability.

Their first simplification attempt is instructive precisely because it failed: they cut back radically and tried creative new ideas at the same time, could not replicate the original performance, and — worse — could no longer tell which pieces had been load-bearing. They restarted with a methodical one-component-at-a-time approach. That method is Module 09.

Exercises
  1. Move the Ralph exit condition inside the agent and script the model to declare victory on iteration 2. You have now reproduced the premature-completion failure mode on purpose. Keep the code as a regression test.
  2. Add a per-iteration cost of $0.40 and a $2.00 ceiling. Which fires first, the budget or the condition? Make the harness report which.
  3. Run the delegation section with ten subtasks instead of five. Does parent context grow linearly? What is the parent's actual scaling limit — and what do you do when you hit it?
  4. Harder: implement no-progress detection across Ralph iterations. If features_done is unchanged for three consecutive iterations, stop and escalate. What should the escalation contain to be useful to a human?
