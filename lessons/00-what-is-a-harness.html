Harness Engineering · Module 00

What a harness actually is

Before any component, one definition. A harness is the runtime that wraps a model and turns it from a text generator into something that can act, remember, and finish. The term is used loosely — we start by drawing the boundary precisely.

Reading + flip cardsno walkthrough25 minCompiled by Premansh Panigrahi

Section 1The definition, and why it matters

A model on its own can only generate text. To have it call tools, work through multi-step tasks, remember what it has done, and keep going until the job is finished, you need a runtime wrapped around the model — and that runtime is the harness.Microsoft Agent Framework documentation

This is the cleanest working definition in the field, and it is useful because it is operational: it tells you what a harness does, not what it is called. But the term is used inconsistently — sometimes for the whole product (Claude Code, Codex CLI), sometimes for the eval scaffold that runs an agent (SWE-bench), sometimes for a framework or an SDK. A 2026 paper by Macedo sets out to fix exactly this.

Section 2Drawing the boundary

Macedo's "What makes a harness a harness" (arXiv:2606.10106) proposes necessary-and-sufficient conditions and an inclusion/exclusion test. The boundary it draws, applied to six real systems:

TermWhat it isIs it the harness?
AgentThe model + loop + state, acting in an environment— (the thing the harness makes possible)
Agent SDKA library of primitives you assemble yourselfNo — a toolkit, not the runtime
Agent FrameworkOpinionated, batteries-included scaffoldingOverlaps; often is the harness in practice
Agent HarnessThe runtime that drives the loop, tools, context, safetyYes
Eval harnessThe scaffold that runs an agent against tasksNo — a harness for measuring, not for acting
OrchestratorCoordinates multiple agentsNo — sits above the single-agent harness

The distinction that matters most in practice: the product you use (Claude Code) contains a harness, but the harness is the layer, not the brand. When you "engineer the harness," you are working at the layer — not configuring the product's UI.

Section 4Where harness engineering sits

Two neighbouring disciplines get confused with it:

  • Prompt engineering shapes what you say to the model, once. Harness engineering shapes the system the model runs inside, every step.
  • Context engineering is a sub-discipline of harness engineering — the part concerned with what the model can see at each step (Module 03). It is not the whole thing; safety, tools, and state are separate concerns that context engineering does not cover.
Harness
The runtime wrapping a model: loop, tools, context, safety, state. Turns text-gen into action.
Loop
The repeat: ask the model, run what it asks, observe, append, decide to stop. The agent is the loop.
Context
What the model can see at each step. A finite, degrading resource the harness must manage.
Eval harness
A scaffold that runs an agent against tasks to measure it. Not the acting harness — a measuring one.
Framework
Opinionated, batteries-included scaffolding. Often is-the-harness in practice (LangGraph, Agent Framework).
Orchestrator
Coordinates multiple agents. Sits above the single-agent harness, not inside it.
